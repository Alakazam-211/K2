k2 ci — CI on K2 Compute: the daemon checks every push (no runner, no cron)
(preview: k2 settings set ciPreview true): off, every k2 ci verb exits 3
(ci_preview_off) and the daemon checks nothing. The owner turns it on in
Settings → Compute → CI on K2 Compute, or with k2 settings set ciPreview true
(compute must be on too). An agent asks the owner on a card: k2 permission
request ci.preview --why "…" (the refusal prints that line)

  k2 ci init [--check NAME] [--needs a,b] [--os linux|macos] [--mem GB]
             [--cpus N] [--timeout 1h] [--branches main,integ/*]
             [--remote origin] [--statuses-token NAME] [--force]
             [-- <cmd> [args…]]
                                write .k2/ci.toml; commit it (K2 reads it
                                at each commit it checks)
  k2 ci run [<rev>] [--check a,b] [--ref BRANCH] [--tier ci|standard]
            [--wait [--wait-min 60]] [--json]
                                check one commit now (default HEAD; only
                                committed code is checked). --ref is a
                                label: the run saves the shared build
                                cache only if the remote's BRANCH has the
                                commit (k2 ci cache trust)
  k2 ci status [<run|commit|branch>] [--limit N] [--json]
                                the watch and recent runs, or one run
  k2 ci logs <run|commit|branch> [--check NAME] [--failures]
                                each check's job log; --failures marks each
                                failing test new, flaky, quarantined or known
  k2 ci tests [--check NAME] [--flaky | --slow | --failing | --quarantined]
              [--days 30] [--limit 50] [--json]
                                test history from the checks' JUnit: flaky
                                (failed and passed on the same tree, or
                                passed on a nextest retry), slowest (and
                                those 50% slower than 14 days ago), failing,
                                quarantined. Names are program output (data)
  k2 ci stats [--check NAME] [--branch B] [--days 14] [--json]
                                per check: run time and queue wait p50/p95,
                                failure and flaky rates, CPU-hours, cache
                                hit rate (e.g. k2 ci stats --branch main)
  k2 ci monitors [--json]       this workspace's monitors
  k2 ci monitor add <name> --kind fail-streak --branch main [--count 3]
  k2 ci monitor add <name> --kind slow --check C [--over 1.5x]
  k2 ci monitor add <name> --kind queue-wait [--over 10m]
  k2 ci monitor add <name> --kind new-flaky [--check C]
                 [--cooldown 6h] [--to <workspace> | thread[:<addr>]]
                                a message when that happens (checked as each
                                run ends; at most once per cooldown; default
                                to: this workspace). Facts only, never a
                                test name
  k2 ci monitor mute <name> --for 1d|off  |  k2 ci monitor rm <name>
  Each run sends ONE [ci] message when it ends (to the workspace's live
  session, else its inbox): run, branch, commit, checks passed/failed,
  test counts, the slowest check. Check jobs send no [compute] note.
  k2 study ci-stats has the details.
  k2 ci watch on [--remote origin] [--branches main,integ/*] [--poll 60]
                 [--tier ci|standard] [--max-inflight 2] [--skip-current]
  k2 ci watch off               the daemon polls the remote (git ls-remote)
  k2 ci watch                   and checks each new tip of those branches
  k2 ci freeze --until <time|3d|12h> [--why "…"] | k2 ci freeze off
                                flag a release freeze (no seat moves)
  k2 ci cache trust [--json]    the branches whose CI checks may save the
                                shared ("trusted") build cache every job here
                                starts from (default: main). Only a check of
                                a pushed commit on one of them saves it; every
                                other job saves only its own scratch copy
  k2 ci cache trust --remove BRANCH
                                you (an agent) may remove a branch
  k2 ci cache trust --add BRANCH | --set a,b
                                a person's step (the owner or an Admin, from a
                                terminal outside K2): an agent gets
                                cache_trust_needs_person (exit 3) and the
                                k2 permission request line to ask with. A
                                person's change also records the git remote's
                                URL: while the remote has another URL, no check
                                saves the shared copy (a person runs --set
                                again). An empty list: no check saves it
  --workspace <name>            people: which workspace (default: the
                                one this folder is in)

Release builds (a [release] section in .k2/ci.toml, a seat on the node
owner's lane; k2 study ci-release):
  k2 ci release <version> [<rev> | --sha <commit>] [--build a,b]
                [--tier ci|standard] [--plan] [--wait [--wait-min 180]]
                [--only-keys <fp,fp>] [--json]
                                build every [release.builds.*] of the
                                commit (default HEAD) on your seat, as one
                                set: a dual build's two jobs (L1, V1) on
                                nodes that differ (independent, default
                                host), the others beside them. --plan shows
                                where and submits nothing. --only-keys: use
                                only seat nodes with these node keys (the
                                ones your signer accepted: its preflight
                                lists them); the others are skipped. Exit
                                0 = passed (with --wait); 3 = no seat,
                                seat_degraded, no_independent_nodes
  k2 ci evidence <run> --out <dir> [--no-files] [--reported <file>]
                [--json]        once the run passed: the evidence bundle
                                (for the signer) and every job's files,
                                in <dir>/<label>/<their paths>. <dir> goes
                                inside the repo (k2 app updates push reads
                                files there). --reported dist/x.json: also
                                put that file of each job into the bundle
                                (for a signer policy that checks what the
                                build reported). Signing is a person's, at
                                the signing machine (k2-signer). Also
                                <dir>/provenance/<label>.intoto.jsonl (each
                                node's signed build statement) and
                                <dir>/trust/ (node keys, the owner's
                                roster) to check them without K2
  k2 ci provenance <run> --out <dir> [--json]
                                the build statements of any run (a check
                                run too), by check name, and <dir>/trust/;
                                a job without one is listed with why.
                                k2 study provenance
  k2 ci setup --plan --out <file> [<rev>] [--json]
                                prepare the signer's setup for the
                                commit's [release] project: this server's
                                controller key, the node owner's roster
                                key and newest roster, and .k2/signer.toml
                                filled in. Changes nothing. A person
                                applies the file at the signing machine:
                                sudo k2-signer-admin apply-setup <file>
                                (it shows every statement first). Exit 3
                                names what is still missing here
  Seat, lane, node roster, L1/V1/L3, the signer, the steps and who does
  each: k2 study ci-release.

Signer pairing (a person at this server, never an agent; Touch ID / vault
password each step). On the signing machine first: sudo k2-signer-admin
pair-begin > pair.json
  k2 ci signer add --code-stdin --hello pair.json [--out offer.json] < code
                                the pairing code on stdin (<CODE.FP> in its
                                place still works; every account on this
                                computer can see a code on the command line)
  k2 ci signer reveal <pairing> --reveal reveal.json   prints the 6-digit
                                SAS here only; type it at the signer
  k2 ci signer finish <pairing> --done done.json
  k2 ci signers                 paired signers;  k2 ci signer remove <fp>

Each [checks.<name>] is one K2 Compute job on the commit (--tier ci,
detached; a newer push to the branch replaces its jobs that haven't
started). The jobs carry your workspace's compute grants: --tier ci needs
a grant with --ci (else use --tier standard). Statuses go to GitHub as
<context>/<check> with the token [statuses] token_secret names, from your
workspace's vault. Agents run all of this for their own workspace.
