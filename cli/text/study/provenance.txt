k2 study provenance — Build statements: what a node signs about a build, and
how to check one (CI preview: every verb here answers ci_preview_off until
the owner runs k2 settings set ciPreview true)

WHAT IT IS
  When a compute job keeps files (k2 compute run --artifact GLOB), its node
  (k2-node 0.46.13 or newer) signs a BUILD STATEMENT beside the job's
  receipt: the commit, the command, the --env names and values, the secret
  names (never values), the machine, how the job was walled off, and the
  sha256 of every file it kept. The node signs with its own key after the
  job's processes are gone, so the job can't write or change it. The format
  is standard: an in-toto Statement v1 with a SLSA Provenance v1 predicate,
  in a DSSE envelope, one JSON line per job (<name>.intoto.jsonl). Spec:
  docs/provenance-v1.md in K2's repo.
  It proves "this node says it built these bytes from this commit with this
  command". It does not prove the node is honest, the build reproducible or
  the source safe. The node OWNER (the K2 server the node belongs to) signs
  a ROSTER: its list of node keys and machines, signed with its ROSTER KEY.
  The owner's roster and a second build on another machine narrow what one
  bad node can do (k2 study ci-release).

WORDS
  job = one compute job; a CI run has checks, each check is one job.
  node key = the key a node signs with; this server recorded it when the
  node joined (enrolled), and k2 compute verify checks against that record.

GET IT
  k2 compute provenance <job>             print the .intoto.jsonl line
  k2 compute provenance <job> --out F     write it to the file F
  k2 ci provenance <run> --out <dir>      every check of a CI run (any run):
                                          <dir>/provenance/<check>.intoto.jsonl
  k2 ci evidence <run> --out <dir>        a release run: the evidence bundle,
                                          with the same files beside it
  Both k2 ci verbs also write <dir>/trust/: nodes/<fingerprint>.pem (each
  node's public key), statements/ (the nodes' signed self-statements), and
  owners.json with rosters/ (each owner's roster as this server held it).

CHECK IT
  k2 compute verify <job | file.intoto.jsonl> [--file PATH] [--owner-key FP]
  --file PATH: a file on THIS machine; K2 hashes it here and checks that
  its sha256 is one the statement names. --owner-key FP: the owner's roster
  key fingerprint, 64 hex (k2 compute owners shows it; it is not a node
  key). It checks, in this order, prints a line for each, and stops at the
  first that fails:
    node key    the key that signed is this server's record for the node
    receipt     the job's receipt verifies with that key
    statement   the signature, the format, and that it agrees with the
                receipt (files and their sha256, commit, command, times)
    plain env   no --env name is also a secret's name in the vault
    file        with --file: as above
    owner       the owner the statement names: when this server holds that
                owner's roster, it must list the node key as active. With
                --owner-key, the statement must name that owner, this
                server must hold its roster, and a node that held no roster
                when it signed can't pass
  Exit 0 = verified; 1 = not (the failed check is named); 2 = bad usage;
  3 = no statement, or refused (code: hint on stderr).
  It checks THIS server's records and is meant for agents. A release signer
  (k2-signer) checks everything again with keys it pinned itself. Outside
  K2 today, a stock DSSE tool checks the signature alone with
  trust/nodes/<keyid>.pem (the keyid is in the envelope); the owner and
  roster checks need a K2 verifier.

NO STATEMENT? (no_statement, exit 3; its hint says which)
  - the plan didn't ask: the node's k2-node is older than 0.46.13, or the
    CI preview was off when the job was sent. Ask the owner to update the
    node or turn the preview on, then run the job again;
  - the job kept no files: run it again with --artifact GLOB;
  - the node sent none (e.g. a job its k2-node took over after an update):
    run the job again;
  - this server refused the one the node sent (it didn't match the
    receipt, or its signature or key was wrong; k2 compute events lists
    provenance_refused): tell the node's owner; don't trust that job.

SECRETS AND --env
  A statement holds the job's plain --env values. Send a secret with
  --secret NAME, never with --env. K2 won't keep or hand out a statement
  whose --env name is also a secret's name in the vault
  (provenance_secret_in_env, exit 3). The value already went to the node
  and into its statement: have the secret rotated, then run the job again
  with --secret.
