Agent isolation (Linux servers)

LABELLED BY AGENT (on wherever the server can have it)
  Every terminal, `k2 job` run and published service of an agent runs in
  that agent's own cgroup, agents/a-<workspace id>/ inside the daemon's
  unit. K5 does this with the standard Linux kernel; no custom kernel.
  - Labelled: each process an agent starts carries its agent's label
    (systemd-cgls, ps -o pid,cgroup,cmd, k2 agent whois <pid>). A fenced
    agent can't write to its cgroup files. Until the Unix-socket block
    lands it can still reach programs of the same user over Unix sockets
    (systemd's buses, your tmux), which can move it or run commands for it
    outside its fence.
  - A copied terminal or job passport alone no longer works: the daemon
    accepts it only on that session's own socket, only from a process in
    that agent's cgroup (else 403 passport_wrong_cgroup, with an audit row),
    and never over loopback TCP (403 passport_needs_socket), whether it
    comes as a Bearer, ?token=, a session cookie or a form body. `k2` in an
    agent's terminal or job sends its passport over the session socket by
    itself. Not bound, so these still work as before when copied: App exec
    passports, microVM cells, and terminals started before 0.46.17.

  Who places the sessions decides the rest. With the root helper (protocol
  19; /boot-status agentIsolation says "identity": "on") each agent's cgroup
  is root's: an agent can't write itself into another agent's cgroup.
  Until the bus policy lands, an agent without the fence can still ask
  systemd to put a process of its own there.
  Without it ("identity": "unavailable", "traceable": true) the daemon
  places them in cgroups the server's user owns, so an agent without the
  fence can move a process into another agent's cgroup.

  What it doesn't do, for an agent without the fence: that agent runs as
  the server's user, the same user as every other agent. It can make
  another agent's session run its commands (through that agent's files,
  the owner token on disk, or ptrace where the kernel allows it), it can
  move any agent's processes out of their cgroup (that drops their label
  and their passport stops working), and it can call as the owner. A
  fenced agent can't do these directly, but until the Unix-socket block
  lands it can still reach systemd's buses and your tmux, which can do
  them for it. Fencing an agent does not protect it from an unfenced one.

  Agent scopes (the owner's switch, off until turned on): k2 agent
  isolation layout on gives every new session, job run and service its own
  root-owned systemd scope outside the server's own service, placed by the
  root helper (protocol 19). It asks for this computer's owner check first.
  Running sessions keep their place until they restart. k2 agent isolation
  layout status says what is live and, when scopes are off, why. An agent's
  own `layout on` is refused (exit 3); with permission cards on it ends with:
      k2 permission request agent.isolation-layout --why "<what you need it for>"
  The owner still has to run `layout on` themselves for the owner check.

  Where it's unavailable (macOS, a user-unit install, a box prepared before
  0.46.16, a container) passports work as before; /boot-status
  (agentIsolation) and k2 app doctor (agentIdentity) say so and why.
  Emergency off-switch for a broken box: K2_AGENT_CGROUP_IDENTITY=0 in the
  daemon's environment (logged at boot, shown in the doctor).

  Open agents are not fenced: for an agent without the fence, its limits
  and K2's port rules stop accidents, not an agent that sets out to get
  around them. Only fenced sessions are held. k2 agent isolation layout
  status says whether this box is a server or a desktop (the rules differ).

THE FOLDER FENCE (per agent, off by default, the owner's switch; experimental)
  k2 agent isolation <workspace> fence. The agent's next terminals, job runs
  and services open only their workspace, their own temp folder, their own
  harness login and the build caches, and read the system and the
  toolchains (Landlock). Not a sibling's folder, not ~/.k2 (owner token,
  vault), not ~/.ssh; no sudo; no writes to their cgroup files. A terminal
  that can't be fenced doesn't start (it says why); never silently
  unfenced. An agent can't turn its own fence off.

  A fenced session's first program runs under a supervisor that, for now,
  only records each Unix-socket connect (in ~/.k2/agents/<workspace>/
  sockblock.log, which the owner reads; nothing is refused yet). Anything
  the session leaves running in the background ends when its first program
  ends. While the supervisor handles a blocking connect, a signal the
  program catches (a handled Ctrl-C, a timer) waits until the connect
  returns.

  Not yet a boundary: Unix sockets (systemd's buses, your tmux or screen,
  an ssh-agent, a container socket) and, on kernels before 6.12, signals
  to other processes aren't blocked. Through those sockets a fenced agent
  can run commands outside its fence (systemd-run --user, a new tmux
  window) or ask systemd to move its processes. The next step closes them.

  Inside a fence, something refused reads "Permission denied". Builds in the
  workspace, git in the workspace, and the shared caches (cargo, npm, bun,
  pip, uv) work. Installing software (brew, apt, cargo install, npm -g) and
  ssh with your keys don't: ask your person.
